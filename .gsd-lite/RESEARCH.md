### 1.2 完了の経路は root 固定（R2 / R3 の分岐点）

- `complete_http` / `complete_storage` / `complete_file` / `complete_rpc` / `complete_host` / `progress_host`（`lib.rs:806-973`）はすべて `self.root.<queue>.consume(id)` → `self.root.package.<definitions>[&name].handler` → `self.root.engine.call_fn(... self.root.state.clone(), response)` → `self.commit_state(next)`。**7 本の本文は「どの Instance か」以外同形**なので、`Instance` のメソッド（例 `fn complete_http(&self, id, response) -> Result<Dynamic, String>`。`run_event` と同じく候補 state を返すだけ）に切り出し、`Runtime` 側は `instance(path)?` で引いて `commit_event(path, next)` に渡せば R3「子への dispatch と同じ経路」（emit → listeners → config → 1 commit）が**そのまま**成り立つ。`commit_event`（`:614-626`）は key が空でなくても動く（dispatch が既に子 key で呼んでいる）
- `commit_state(next)` = `commit_event("", next)`（`:1018-1020`）。子の完了は `commit_event(path, next)` を直接呼ぶ
- エラー文言の既存の付け方: dispatch は子のエラーに `Component {key}: ` を前置（`:602`）。完了も同じ前置にする（`{script} / HTTP {name} / {handler}: {e}` は Instance 側で組み、Runtime が `Component {path}: ` を足す）
- `dispatch` の `dialogs::Event::Answer(id, data)` → `self.complete_dialog(id, ...)`（`:586-588`）。**ダイアログの回答は event 経路から来る**ので、どの Instance の handler かは `pending[id]` 側が知っていなければならない（§1.3）
- `clear_queues`（`:568-573`）は既に root + 全子の 6 キューを空にする。`pages.clear()` / `dialogs.clear()` は共有キュー。完了 7 本の先頭でこの 3 つを呼ぶ順序は現状のまま（`complete_http` だけ `consume` が `clear_queues` より前。`:861-863`。順序を揃えるなら照合で差分 0 を確認）

### 1.3 共有キュー `dialogs` / `pages` には「どの Instance が積んだか」が無い

- `dialogs::Intent`（`dialogs.rs:105-113`）は `operation / message / default_value / handler / icon / draft`。`prepare(&self, ast: &AST)`（`:222-240`）は **root の AST** で handler の存在を見る（`commit_all` `lib.rs:1048`、`Instance::load` `instance.rs:216` は自分の AST）。`consume` は handler 名を返し、`complete_dialog` が root で実行する
- `pages::Requests::prepare(definitions)`（`pages.rs:54-68`）も `commit_all` から **root の `package.pages`** で引く。`Instance::load:217` は自分の `pages` で引く（init 中の navigate 拒否）
- どちらも `register` の closure にキューしか持たせていないので、**同じ `Requests` を子 Engine に登録すると積んだ主が分からない**。選択肢:

  | 案                                                                                                                                                                                                            | 差分                                                                                                                   | 評価                                                                                                                                                                                                                          |
  | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
  | (T) origin タグ: `register(&self, engine, origin: &str)` にして Intent に `origin: String`（接頭辞付きパス。root は `""`）を持たせる。`prepare` は `origin` ごとに `instance(origin)` の AST / `pages` で検証 | `dialogs.rs` / `pages.rs` の Intent + register + prepare、`Instance::load` に `path` 引数、`commit_all` で検証先を引く | **推奨**。キューは root 1 本のまま（DECISIONS「dialog のキューは root 1 本」「navigate は画面全体の遷移」と一致）。`At most one navigation per handler`（`pages.rs:41`）が「1 トランザクションに 1 遷移」として画面全体で効く |

### 1.4 `take_effects` と `commit_all` は root のキューだけを見る

- `take_effects`（`lib.rs:995-1014`）の連結順 `http → storage → files → rpc → dialogs → pages → host` は応答の `effects` 配列そのもの（`components-plan.md:139`）。root の順序は不変にし、**子は root の後ろに `components`（BTreeMap = パス順）の順で同じ 5 種（http → storage → files → rpc → host）を連結**するのが最小。dialogs / pages は root 1 本のキューなので、子由来のものも root の位置に出る（`instance` だけ付く）
- `commit_all`（`:1024-1083`）は子の `prepare_commit` → **root だけ** `http / host / storage / files / rpc` の `prepare` → `dialogs.prepare(&self.root.ast)` → `pages.prepare(&self.root.package.pages)` → navigate 排他（`:1050-1061`）→ `buffers::capacity` → `apply` → `commit`。段階 4 では**全 Instance の 5 キューを `prepare` し、どれか 1 つでも失敗すれば全部捨てる**（`prepare` は `std::mem::take` でキューを空にするので、失敗後に残りの Instance のキューが残っても次の入口の `clear_queues` が消す = 段階 3 の F1 と同じ性質）。navigate 排他は「全 Instance の intent 合計」で判定する。`buffers::capacity` も全 Instance の file / rpc の合計
- `apply` は失敗しない処理だけ（`:1065-1081`）。子の `commit` 5 本もここに並べる

### 1.5 `instance` を受ける ABI と公開シグネチャ（受け入れ 7）

- `abi.rs:67-111` の 7 op は `request.get("id")` → `runtime.complete_*(id, ...)`。`instance` は `request.get("instance")` で読む。**JS の `JSON.stringify` は `undefined` を落とすが `null` は残す**ので、受理する形は「キー無し = root」「文字列 = 子」の 2 つにし、`null` / 数値 / 空文字列は `Invalid component instance` とする（§7-7）
- `Runtime` の `pub fn` 名と引数は不変（受け入れ 7）。選択肢: (a) `complete_http_in(&mut self, instance: &str, id, response)` のように 7 本を足し、既存 7 本は `""` で委譲（抽象度は低いが機械的）/ (b) `pub enum Completion { Http{id, response}, Storage{..}, File{id, response, buffer}, Rpc{..}, Host{..}, HostProgress{..}, Dialog{..} }` と `pub fn complete(&mut self, instance: &str, completion: Completion)` を 1 本足し、既存 7 本は `complete("", ...)` の薄い wrapper にする。**(b) を推奨**（新しい pub fn が 1 本、ABI の `match` も 1 箇所にまとまる）。どちらも DECISIONS に書く
- `instance` の解決: `Runtime::instance(path)`（`:765-770`）が `Unknown itemId: {path}` を返すが、完了の未知 instance には**別文言**（例 `Unknown component instance: {instance}`）が要る（`Unknown itemId` は event の文言。`abi-errors` 列の期待値に触らない）。形の検査（空要素 / 先頭末尾の `/` / `:` を含む）は `Invalid component instance`
- 不正な完了の分類と文言（R2）。既存文言で済むものが多い:

  | 入力                                                              | 判定箇所                        | 文言                                                                                                                                    |

  | 未知の `instance`                                                 | Runtime                         | 新規 `Unknown component instance: {instance}`（案）                                                                                     |
  | `instance` の形が不正（`null` / `""` / `a//b` / `:`）             | abi.rs                          | 新規 `Invalid component instance`（案）                                                                                                 |

### 1.6 storage / files の scope（R5）: 規則・検査位置・**`__` の曖昧さ**

- 現状の検査: `storage::safe_key`（`storage.rs:49-55`。`[A-Za-z0-9_-]{1,80}` バイト）。`Instance::load:147-151` は `storage` を宣言する package の `id`、`:168-170` は `files` の `id` を検査。JS は `storage-client.js:3`（同じ正規表現）、`opfs.js:1`（`safeName`）、`fileLockKey(scope, volume)`（`opfs.js:35-38`。`uivolve-web:file:${scope}:${volume}`）、`application-loader.js` では未検査
- itemId の文字制限は `:`（`lib.rs:1522`）と `/`（`:1525`）だけ。`.`・空白・非 ASCII・`_` の連続はすべて通る。したがって `<root id>__<path の / を __ に置換>` は:
  - itemId `a__b` を持つ子と、`a` の下の `b`（パス `a/b`）が**同じ scope `orders__a__b` になる**（Pulumi が `::` と `$` を分けた理由と同型。§4）。root の `id` に `__` が入る場合も `orders__a` + `b` と `orders` + `a/b` が衝突するが、これは「画面 id の衝突」という既存クラス
  - 非 ASCII の itemId は合成後に `safe_key` で落ちる（規則どおり load エラー）
- **推奨**: 規則はそのまま、「scope を構成する要素（root の `id` と各 itemId）は `__` を含まない」を load エラーの条件に足す（§7-1）。検査は `Composing::load`（`lib.rs:450` の直後。子の `package.storage` / `files` が空でないときだけ）で `format!("{root_id}__{}", path.replace('/', "__"))` を組んで `safe_key` + 要素の `__` 禁止。JS は `application-loader.js:#components`（`:136-163`。`countInstances` が同じ走査をしている `:69-82`）で日本語文言。**Rust と JS の規則一致テスト**は「同じ (root id, path) の表を両方に流して同じ可否」が最小（Rust 単体 + Vitest で同じ JSON 表を読む）
- 子自身の `id` の `safe_key` 検査（`instance.rs:147,168`）は段階 4 で**無意味になる**（scope に子の id は使わない）。残すと「id が unsafe な既存画面を部品にできない」が、外すと `Instance::load` の挙動が root と子で分岐する。plan が決める（§7-8）
- JS 側で scope を合成する（REQUIREMENTS R5「JS が `effect.instance` と root の `id` から合成」）なら `StorageEffects.reset(scope)`（`storage-effects.js:22-27`）を「`(effect) => scope` の解決関数」に変える（§2）。OPFS のディレクトリ名としての安全性は §3 のとおり

### 1.7 layout の子スナップショット（R8）

- `layout_scope`（`lib.rs:1091-1100`）は layout ごとに全子の `ui.clone()` + `state_json()` を `BTreeMap<String, (Node, Value)>` に作り、`composition::enter_layout`（`composition.rs:357-369`）が `Rc` で包んで thread_local に置く。参照は `with_component`（`:374-393`）
- **Instance の `state` / `ui` を書く場所は `Instance::apply`（`lib.rs:1400-1403`）だけ**（`git grep -n -E '\.state = |\.ui = ' engine/src` は他に `composition_tests.rs:926` の `set_state` helper のみ）。したがって世代カウンタを持たなくても、`Instance` に `snapshot: RefCell<Option<Rc<(Node, Value)>>>` を持たせ、`apply` で `None` にし、`layout_scope` で `None` なら作って入れる（lazy）だけで「state が変わっていない子の再シリアライズを省く」が成り立つ。`enter_layout` の引数を `BTreeMap<String, Rc<(Node, Value)>>` にする（`Rc::new` の場所が動くだけ）
- 注意: `set_state`（テスト helper）は `apply` を通らずに `state` を書く。キャッシュを入れると **`layout` → `set_state` → `layout` の順のテストが古い Scene を見る**。`set_state` を `apply(state, ui.clone())` 経由に直す（P12）

## 4. 類似 OSS・語彙（similar_oss。サブエージェント調査）

- **Elm**: `Cmd.map` で子の完了メッセージを親の型に包み、親が子へ配る。多段で毎層ラップ型が要る boilerplate が批判されている（<https://discourse.elm-lang.org/t/whats-wrong-with-using-html-map/8105>）。`elm-spa-example` の `Main.elm` は「もう無いページ宛の完了」を `( _, _ ) -> ( model, Cmd.none )` で黙って捨てる。**盗む**: `instance` を平坦なパス文字列にして root が 1 段で解決する（本件の設計と一致）。「現在の木に無い `instance` の完了は拒否して state 不変」は Elm の catch-all と同じ結論（本件はエラー応答にする。R2）
- **Erlang/OTP**: `gen_server:call` は要求ごとの `reference()` で遅延返信を識別し、OTP 24 以降は alias の無効化で「遅れた返信は黙って落とす」（<https://www.erlang.org/doc/apps/stdlib/gen_server.html>、EEP 53）。**盗む**: 「(instance, id) の組が pending にあるか」の一点で受理を決める。reload 後の遅延完了（受け入れ 5）は Runtime が丸ごと入れ替わるので pending が無い = 既存文言で拒否
- **redux-loop / Hyperapp**: `Cmd.map` と「完了先を effect 発行時に固定」。**盗む**: 完了先（`instance`）は effect に載せて echo させ、ホストに解釈責任を持たせない（ExtJS の `opt` と同じ）
- **React / redux-saga**: unmount 後は「結果を無視」が必須で「中断」は最適化。**作らなくてよいもの**: 子 Instance 単位の cancel op。画面置換時の世代番号（`#generation`）で既に捨てている
- **Vuex / Pulumi / Terraform**: 論理パスの区切りは `/` が慣習。Pulumi は型トークンに `:` と `/` が入るので URN の区切りを `::` と `$` に分けた。**警告**: 単一文字でも 2 文字でも、要素にその文字列が現れうる限り曖昧（§1.6）。**盗む**: 区切り文字列を要素から禁止する検査
- **ExtJS**: `store.load({callback, scope})` / `Ext.MessageBox.confirm(title, msg, fn, scope)` の `scope` が「完了を受け取るコンポーネント」。destroy 後も callback が走るのが既知の落とし穴（本件は pending が無ければ拒否）
- 作らなくてよいもの: 無し（既存 OSS で「Rhai + 1 Scene + 1 トランザクション」の子への完了ルーティングを提供するものは無い）

## 7. 要件への影響（提案。REQUIREMENTS.md は書き換えない）

1. **R5 の補強**: 規則 `<root id>__<path>` はそのまま、「scope を構成する要素（root の `id` と各 itemId）が `__` を含むとき、その子が storage / files を宣言していれば load エラー」を足す（P1）。文言は Rust `Component {path}: storage scope {scope} requires 1–80 ASCII letters, digits, - or _ without "__" in any part`（案）、JS は日本語で同旨
2. **受け入れ 1 の免除**: 段階 3 の拒否を検査していたテスト（§1.8 の表 5 件 + probe の 2 列）は R1 で意味を失うので、「`kind: "http"` 起因」とは別に「段階 3 の拒否機構の撤去に起因」として PROGRESS に列挙することを許す
3. **R9 の「http の子で worker mock API から行が出る」**: `http-grid.json` は `../data/products.json`（静的 JSON）を `requests` で取得する画面で、worker mock API（`worker-orders.yaml` の `operations` + `ordersMock` 接続）は使わない。無改修で置く以上、Vitest は `tests/http-grid.test.js` と同じく `resources.text` を差して `data/products.json` を返す形にし、「worker mock API」の語は外す（または host の子を 4 種目として足すかを plan が決める。足すなら `connections` の注入が要る）
4. **R6 の HostEffects 上限**: `同時ホスト操作は8件までです`（`host-effects.js:184`）を Instance ごとにする（R7 と整合）。契約文書の「画面全体では Instance 数 × 上限」にこの 8 も含める
5. **R6 の dialog**: `UiRuntime` には `dialog_result` を送る経路が無い（§2）。`WasmEngine.completeDialog(id, response, instance)` の追加と `docs/dialogs.md:110` の追記で満たす
6. **R2 の dialog 文言**: 子のダイアログの `dialog_result` で `instance` 省略 / 他 Instance は、新文言を増やさず `Unknown or completed dialog request` を再利用する（P13）
7. **R2 の `instance` の形**: 受理は「キー無し」と「`[^/:]+(/[^/:]+)*` の文字列」だけ。`null` / `""` は不正（P9）
8. **子の `id` の `safe_key`**（`instance.rs:147,168`）: scope に使わなくなるので外すか残すかを plan が決める。推奨は**残す**（root と子で `Instance::load` を分岐させない。既存画面の id はすべて safe）
9. **`internals` feature**: 唯一の利用者 `reject_effect_calls` が消えるので外せる（`docs/components.md:155` も消す）。plan が決める（外すなら `Cargo.lock` は `--locked` で通るか impl が確認）
10. **公開シグネチャ**: `pub fn complete(&mut self, instance: &str, completion: Completion)` 1 本 + 既存 7 本を wrapper に（§1.5 (b)）。DECISIONS に書く
11. **件数の追従先**（R10）: `docs/components.md:126,135`（19 個 / 7 種）、`docs/testing.md:88`（変異 5 本・拒否 2 本）、`docs/architecture.md:62,98`、`docs/host-adapters-design.md:46`、`docs/tutorial-http-grid.md:110`、`docs/components-plan.md:3,85-92,99,145-146`、`docs/dialogs.md:110`、`docs/platform-features.md:97`（完了 handler の引数に `instance` は**渡さない**。effect / op だけ）。`README.md` と `blog/` に件数の記述は無い（`git grep -n -E '効果関数|19個|宣言7種|7種|変異5本' -- README.md docs blog` の結果は docs の上記 3 行のみ）
12. 段階 5 への申し送り: 子の descriptors の同梱（§1.9）は段階 4 で ABI に入れるので、段階 5 のローダー改修は「取得・キャッシュ」だけになる
