### 1.2 dispatch（R4）の分岐点

- `Runtime::dispatch`（`lib.rs:427-550`）は root 固定: `find_path(&self.root.ui, target)` → 捨てる条件（最前面 window・disabled・非表示 window・折りたたみ・`navigation::hidden` / `extras::hidden` / `layouts::hidden`）→ 組み込み処理 → `bind` 書き込み → `call_fn` → `commit_state`。
- 接頭辞付き target は `find_path` に失敗して `Unknown itemId` になる。**最初の `/` で分割**し、前半（component itemId）で親側の path を取り、親側の捨てる条件を path に適用してから、後半を該当 Instance へ渡す（R4「親側の経路で先に適用」）。深さ 3 は再帰で `"a/b/c"` → root が `a`、`a` が `b/c`。
- 子へ渡す本文は「`find_path` から `call_fn` まで」= 現在の `dispatch` のうち root 固有でない部分。`Instance` のメソッド（例: `Instance::run_event(&mut self, target, payload) -> Result<Option<Dynamic>, String>`。`None` = 捨てた）に切り出し、root も同じ関数を通す。切り出し後に照合（§5）で差分 0 を確かめる。
- `extras::hidden`（`extras.rs:495`）は toast のみ、`navigation::hidden` は非アクティブタブ・閉じたメニュー、`layouts::hidden` は非アクティブ card。これらはすべて `&[&Node]` と `&Value` だけを取るので子 Instance の `ui` / `state` にそのまま使える。

### 1.3 layout（R3）の挿入点と 3 案

- `layout`（`lib.rs:825-978`）は `measure` / `arrange` / `arrange_sized` / `arrange_children_sized` / `content_height` の自由関数で木を下る。これらと各モジュール（`layouts` / `extras` / `navigation` / `grid` / `kanban`）の `arrange` / `height` の呼び出し箇所は **35 か所**（`git grep -n -E 'measure\(|arrange_sized\(|arrange\(|arrange_children' engine/src`）。
- Scene の `key` は `arrange_children_sized`（`lib.rs:1470-1474`）で「itemId があればそのまま、無ければ `{親key}.{i}`」。`Widget.target` は `widget()`（`lib.rs:1264`）で `node.item_id` そのまま。**itemId を持つ子ノードの key は親の key を継がない**ので、子 Instance の widget は「配置後に `widgets[start..]` の `key` / `target` へ `"<itemId>/"` を前置」する後処理が要る（`payload` は触らない）。`arrange_children_sized` の `disabled` 伝播（`lib.rs:1487`）も `widgets[start..]` に効くので、disabled な親の下の component は自動で無効化される。
- state キーを itemId から作る箇所（`format!("ui_{}...")` 13 件）は **すべて normalize 内**（`grid.rs:18` / `navigation.rs:8` / `layouts.rs:87` / `fields.rs` / `extras.rs`）で、layout / dispatch 時に itemId からキーを計算する箇所は無い（`git grep -E 'lookup\(state, &format|flag\(state, &format'` が 0 件）。
- 子 Instance の `ui` / `state` を自由関数に届ける方法:

  | 案                                                                                                                                                                                                                                                                                               | 差分                                                                         | 評価                                                                                                                                                                                                                                                               |

### 1.4 commit_state（R4 トランザクション）の分割点

- `commit_state`（`lib.rs:762-819`）の前半「検証して `(state, ui)` を作る」（`check_state` → `resolve` → `validate_handlers` → `initialize_added` → `grid::reconcile`（**現在の state を使う**）→ `resolve` → `validate_ui_state` → `stateSchema`）は Instance のフィールドしか使わない。後半は root の 5 キュー + dialogs + pages の `prepare` → navigate 排他 → `buffers::capacity` → 代入 → `revision += 1`。
- 分割案: `Instance::prepare_commit(&self, next: Dynamic) -> Result<Prepared { state: Dynamic, ui: Node }, String>` と `Instance::apply(&mut self, Prepared)`。root は従来どおり `Runtime::commit_state` がキュー処理を挟む。子は `Prepared` を集め、全部通ってから親 → 子の順に `apply`。順序（R4）: 子 handler → emit を親 listener へ順に → 親 state の bind 差分で `config` 更新 → 子 `config` handler → 全 `prepare_commit` → 代入。
- `config` 差分の判定は「親の候補 state と現在の root state で、component ノードの `config` の `{bind}` が指すキーの値（`serde_json::Value` の `==`）が変わった子」。load 時は差分に関係なく全子へ注入（`init` 前）。
- `dialogs.prepare(&self.root.ast)`（`lib.rs:789`）は root の AST だけで良い（子の `alert` 等は拒否されキューに入らない）。

### 1.5 Rhai 関数登録（R4 emit / R5 拒否）

- 既存パターン: `pages::Requests::register`（`pages.rs:35-48`）が `Rc<RefCell<Vec<String>>>` のキューを closure に持たせて `register_fn("navigate", ...)`、`prepare` でキューを取り出し、`load` 時は `!pages.prepare()?.is_empty()` で「init 中の navigate」をエラーにする（`instance.rs:184-186`）。**`emit` は同じ形**: `Rc<RefCell<Vec<(String, Dynamic)>>>`、上限 8、`Dynamic` → `Value` 変換失敗はエラー。`init` 中 / `config` 中の emit は呼び出し後にキューが空でなければエラー。
- 拒否 stub: Rhai は **名前 + 引数の数**で関数を引く。`Dynamic` 型の引数は任意の型に一致するので、「関数名 × 引数の数」ごとに `|_: Dynamic, ...| -> Result<(), Box<EvalAltResult>> { Err("子コンポーネントでは <name> を使えません".into()) }` を登録すれば型の変種を網羅できる。stub が無い arity は Rhai の `ErrorFunctionNotFound`（関数名入り）になるが、R10 の「どの関数か」を自前の文言で出すには一覧が要る:

  | 関数                                                                                            | 引数の数（登録元）                                                                   |
  | ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
  | `http_get`                                                                                      | 1（`http.rs:31`）                                                                    |
  | `host_call` / `host_cancel`                                                                     | 2 / 1（`host.rs:36, 60`）                                                            |
  | `storage_read` / `storage_remove` / `storage_write`                                             | 1 / 1 / 2（`storage.rs:63, 71`）                                                     |
  | `file_read_text` / `file_read_bytes` / `file_mkdir` / `file_list` / `file_stat` / `file_remove` | 各 2（`files.rs:128-138`）                                                           |
  | `file_write_text` / `file_write_bytes`                                                          | 3 / 3 と 4（`files.rs:140-180`。`file_bytes` と `len` は副作用なしなので残してよい） |
  | `rpc_call`                                                                                      | 2（`rpc.rs:90`）                                                                     |
  | `alert` / `confirm` / `prompt`                                                                  | alert 1・2・3、confirm 2・3、prompt 3・4（`dialogs.rs:127-217`）                     |
  | `navigate`                                                                                      | 1（`pages.rs:37`）                                                                   |

  子 Engine には `http` / `host` / `storage` / `files` / `rpc` の `register` と `dialogs.register` / `pages.register` を**呼ばず**、代わりに上の stub を登録する。`Instance::load` の `register: impl FnOnce(&mut Engine)` は最後に呼ばれる（`instance.rs:80`）ので、既存 `register` の後に同名を上書き登録しても同 arity は後勝ちだが、**呼ばない方が明快**（`Instance::load` に「効果を登録するか」の引数を足す）。

- メソッド呼び出し構文 `"name".http_get()` は同じ関数に解決する。stub は名前 + arity で引かれるので同様に拒否される（load 時走査も `Expr::MethodCall` を含める。§3）。
- `with_clock`（`lib.rs:418`）は root の `extension_context` にしか `enter` しない。子の `date_*` 等は子 Engine の context を読む（`extensions/mod.rs:17-47`、Engine ごと）ので、**子すべての context に `enter` する**（`Vec<ClockGuard>` を保持）か、context を Runtime で 1 つ作って全 Engine に渡す（`register_with_context` は `&ExtensionContext` を clone して持つ `Rc<Cell>` なので共有できる）。後者が差分小（P6）。
- `dialogs::SEQUENCE` 等の thread_local（前回 RESEARCH §1.2）は本マイルストーンでも触らない（子は dialogs を使えない）。

## 4. 類似 OSS・語彙（similar_oss）

- **ExtJS**: `listeners: { eventName: fn }` を生成時に渡す。`fireEvent('name', args...)` はリスナーが無ければ何もしない（戻り値 true）。`config` は setter / `updateX` を自動生成し、値の変更時に呼ばれる。本件の対応: `listeners[name] = 親 handler 名` / `emit(name, payload)` / `config` → 子 `state.config` + `config(state, event)`。ExtJS の「リスナーが `false` を返すと以降を止める」「イベントの bubbling」「`scope`」は取り込まない（契約文書に「対応しない」と明記）。出典: Sencha「Events」ガイド <https://docs.sencha.com/extjs/6.5.1/guides/core_concepts/events.html>、`Ext.Evented` <https://docs.sencha.com/extjs/5.0.0/api/Ext.Evented.html>
- **Elm（TEA の入れ子）**: 親が子の model を所有し、子の `Msg` を `Html.map` / `Cmd.map` で親の `Msg` に写す。「translator パターン」= 子が出し得るメッセージの一覧を親が受け取り方を決める。本件の `emit` / `listeners` はこの translator と同型で、子 state は親から見えない（state ownership）。出典: Elm discourse「Commands and messages from/to child models」<https://discourse.elm-lang.org/t/commands-and-messages-from-to-child-models/7665>、`turbomack/glue` <https://github.com/turbomack/glue>
- 一般語彙「props down, events up」（Vue / Svelte）。契約文書では `config`（親 → 子、固定値 or bind）と `emit`（子 → 親）で統一し、組み込み xtype は「ウィジェット（組み込み部品）」（DECISIONS の用語）。
- 作らなくてよいもの: 無し。既存 OSS で「Rhai + 1 Scene + 1 トランザクション」の合成を提供するものは無く、設計は `components-plan.md` の B 案どおり自作する。

## 7. 要件への影響（提案。REQUIREMENTS.md は書き換えない）

- R1 の「`components: Option<BTreeMap<..>>`」は `BTreeMap` + `skip_serializing_if = "BTreeMap::is_empty"`（既存の `requests` と同形）で満たすことを提案（意味は同じ、`Option` の分岐が減る）。
