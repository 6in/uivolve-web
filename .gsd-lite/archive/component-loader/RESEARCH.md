### 1.5 2 MB の 2 段構えと「合計」の基準（R4。計測）

- 既存: JS `engine.js:60`（`call` の JSON バイト数）と `:114-125`（子同梱時に合計と最大の子を文言に出す。最大の子は `JSON.stringify(entry)` のバイト数）、Rust `abi.rs:181`（入力長 `len > 2_000_000`）。**descriptor は JSON リクエストに入らない**（`storeBuffer` で別経路。`engine.js:86`。1 件 1 MB・合計 16 MB・32 件 `docs/files-cache-rpc.md:181`）
- 計測（`scratch/turn-001-size-probe.mjs`。同梱デモの生ファイル合計 source+script と、`load` リクエストの JSON バイト数）: `parts-lab.json` 4 パッケージ raw 7,299 / JSON 6,714（比 0.920）、`order-dashboard.json` 2 パッケージ raw 4,066 / JSON 3,523（0.866）、`http-grid.json` 1 パッケージ raw 3,380 / JSON 3,148（0.931）。整形済み JSON は `JSON.stringify` で縮むので、**生バイト合計 > 2,000,000 でも load は通りうる**（逆に YAML が JSON より大きくなることもありうる）。つまりマニフェスト段階の拒否は「粗い前段」で、load 時の検査が正。network-only では通る木が network-first では拒否される境界（raw 2.0〜2.3 MB 付近）が存在する。採用済み（DECISIONS「据え置き + 早期拒否」）だが、**文書に「合計は生バイト、load は JSON 化後」と書く**
- **合計に descriptor を含めるか**（§7-1）: 含めると「root 1 MB + descriptor 8 × 1 MB」のような現状 load できる画面（descriptor は buffer ABI）を新しい前段が拒否する。含めないと R4 の文言「木のファイルの `size` 合計」から外れる。推奨は**含めない**（`load` が同梱するのは package と script だけ。descriptor には既に 1 MB / 8 件 / 16 MB の上限がある）
- 受け入れ 2(e)「取得回数 0」の読み方: マニフェスト自体は `resources.text` で 1 回取得される。検証は「`resources.bytes` が 0 回」または「fetcher の呼び出しがマニフェスト URL の 1 回だけ」（`components-loader.test.js:56-64` の `reads` Map がそのまま使える）

### 1.6 Rust: `take_instance` と 256 バイト（R6 残留リスク 1）

## 7. 要件への影響（提案。REQUIREMENTS.md は書き換えない）

1. **R4 の「合計」の定義**: 「木のファイルの `size` 合計」を「全パッケージの `source.size + script.size` の合計（descriptor を含めない）」にすることを推奨（§1.5）。含めると現状 load できる画面（descriptor は buffer ABI 経由で JSON リクエストに入らない）を新しい前段が拒否する。plan が決めて DECISIONS に書き、`docs/files-cache-rpc.md` / `docs/components.md:226-231` の「2 段構え」に「マニフェスト段階は生バイトの粗い前段、load 時が正」を書く
2. **R6 の対称性**: `instance` の 256 バイト上限を**load 時にも**掛ける（Rust `Composing::load` のパス合成時 `Component {path}: instance path exceeds 256 bytes`、JS `instanceTable` で日本語）ことを推奨（§1.6）。掛けないなら契約文書に「接頭辞付き itemId は 256 バイト以内」を書く。どちらでも `docs/components.md` の制限表に 1 行（R6 のとおり）
3. **受け入れ 2(e) の読み方**: 「取得回数 0」は「マニフェスト以外のファイル取得 0 回」（マニフェストの `resources.text` 1 回は必要）。plan は `resources.bytes` の回数または fetcher の URL 一覧で書く
4. **R5 の認証の契機**: 「`getAuthentication()` の結果（`mode` / `allowedOrigins` / `refresh` のメタデータ）が変わったとき」と明記し、「トークンだけの差し替えは検知しない」を契約文書に 1 行（§1.4）
5. **R3 の `fallbackReason`**: 復元が `previous` に落ちたとき、現在版のどの子で失敗したかを `fallbackReason` か `onCache` に添える（文言は既存のまま、URL を足す。R3「どの子で失敗したか URL を出す」と整合）。plan が `main.js:171-180` の表示を変えるかを決める（変えなくても `fallbackReason` に入る）
6. **R9 の追従先の追加**: `docs/files-cache-rpc.md:102,104,106,185`（REQUIREMENTS は `:82-100`）。`docs/runtime-distribution.md:40` は無改修でよいが plan の表に「無改修と判定」の行として載せる（前回の Minus 1 = 行数の突き合わせ）
7. **受け入れ 7 の補強**: `bun run build:wasm` 後に `public/screens/http-grid.json.manifest.json` も version 2 で `components: {}` を持つ（子なし画面の再生成。R1 のトレードオフの実測）
8. **テストの置き換え**: `tests/components-loader.test.js:190-214` の「キャッシュ経路の拒否」は削除し、同ファイルか `tests/files-cache-rpc.test.js` に木の保存・復元を置く（受け入れ 2 の列挙。`memoryOpfs` と `cacheFixture` の形は `files-cache-rpc.test.js` にあるので、plan は**どちらのファイルに置くか**を決める。`docs/testing.md:41` の行を追従）
9. **段階 6 への申し送り**: 共有は子パッケージの Map だけで、root は共有しない。WebMCP 合成で root のツール面を組むときも共有を参照しない
