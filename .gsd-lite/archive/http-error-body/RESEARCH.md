### 4.3 4xx を「処理していない」とみなす前例と 408 / 429 の除外

| ソース                  | 再送してよい（処理前の失敗）とみなす条件                                                                                                                                                                      | 出典                                                                                               |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| Azure SDK（azure-core） | 既定 `[408, 429, 500, 502, 503, 504]`。400 未満は再試行しない                                                                                                                                                 | <https://learn.microsoft.com/ja-jp/python/api/azure-core/azure.core.pipeline.policies.retrypolicy> |
| AWS SDK                 | **エラーコード優先、ステータス後置**。`RequestTimeout`（400 でも）/ `Throttling*` / `TooManyRequestsException` は transient。旧版は 408 / 429 を transient に含めると明記                                     | <https://docs.aws.amazon.com/general/latest/gr/api-retries.html>                                   |

- 408 / 429 を除く根拠: Azure・AWS 旧版・Stripe が共通して 408（本文を待ちきれず**処理前に**切った）と 429（**処理前に**拒否）を「再送してよい」側に置く。他の 4xx は IETF draft「Clients MUST correct the requests」に当たる
- 注意 2 点: (a) AWS は 400 でも `RequestTimeout` コードがあれば transient = **ステータスだけでは分類できないサーバがある**、(b) Stripe は「実行開始後の 400」をキャッシュする = **4xx を返す前に副作用が起きる API もある**。→ R3 を**接続単位の opt-in（既定 `unknown`）**にした DECISIONS と整合する。将来の拡張点として、応答ヘッダ（`Stripe-Should-Retry` 型）で `failed` / `unknown` を上書きする形を残す余地がある（要件外。§7-5）

### 4.4 冪等キーを画面側（クライアント）が持つ運用

- Stripe: UUID v4 等のランダムなトークン。再試行は同キー同パラメータ、24 時間。パラメータを変えるなら**新キー**。409 は同キーで待って再送（<https://docs.stripe.com/error-low-level>）
- Shopify: UUID v4 / v7。「Avoid generating a new random UUID every time you call the mutation」。同キー異パラメータは `IDEMPOTENCY_KEY_PARAMETER_MISMATCH`（<https://shopify.dev/docs/api/usage/implementing-idempotency>）
- Square: `idempotency_key` は **JSON 本文**の必須フィールド（最大 45 文字）。同キー異本文はエラー、同キー同本文は元の成功応答（<https://developer.squareup.com/docs/build-basics/common-api-patterns/idempotency>）。**ui-bridge の `idempotencyKey`（本文）と同型**
- IETF draft: UUID 推奨。「MUST NOT be reused with another request with a different request payload」
- brandur.org: キーは「ユーザーの意図」を表す。最初の試行前に生成し、結果不明なら確定応答まで同キーで再試行（<https://brandur.org/idempotency-keys>）
- 生成のタイミング（「送信時 1 回」vs「表示時」）を正面から扱う公式文書は無し。公式の一致点は「1 つの論理操作に 1 キー・再試行は同キー・入力が変われば新キー・成功したら捨てる」。推測（サブエージェント）: state に持つなら「最初の送信で生成し、`unknown` の間は保持、成功またはユーザーが入力を変えたら破棄」が規則を最も素直に満たす（「送信ボタン押下ごとに生成」だと再送ボタンで新キーになる事故が起きやすい）。R6 のデモはこの形で書く

### 4.5 API モック（Worker / Service Worker）の固定の失敗応答

- MSW: `HttpResponse.json(body, {status: 422})`。**`Content-Type` は init.headers に無いときだけ** `application/json` を付けるので、`headers: {"Content-Type": "application/problem+json"}` を渡せばそのまま（<https://mswjs.io/docs/api/http-response>）
- Prism: 既定は「lowest 2XX」、`Prefer: code=422` で指定、検証失敗は仕様に無ければ Prism 自身が `application/problem+json`（`type/title/status/detail/validation[]`）を生成（<https://raw.githubusercontent.com/stoplightio/prism/master/docs/guides/02-request-validation.md>）
- Mirage: `new Response(400, {headers}, {errors: [...]})`
- 含意: Worker モックの固定応答に `headers`（省略時 `application/json`）を足すなら MSW の契約を写せる（§5-E）。足さなくても R1 の受付は通る（`application/json` も受け付ける）

### 4.6 WASM にホストから乱数を注入する前例（import 無し）

- 使えない根拠: `getrandom` は `wasm32-unknown-unknown` で既定非対応。`wasm_js` backend は wasm-bindgen 経由で `crypto.getRandomValues` を **import** する。`custom` backend は `__getrandom_v03_custom` を Rust 側で定義する方式で import は増えないが「project で 1 回だけ定義」の制約つき（<https://docs.rs/getrandom/latest/getrandom/>）。`rhai-rand` は `rand = "0.9"` に依存し `rand::rng()` が getrandom 必須（<https://docs.rs/crate/rhai-rand/latest/source/Cargo.toml>）→ **本件では使わない**
- import 方式の前例: WASI preview1 `random_get`（`wasi_snapshot_preview1` の import。wasi-random は「決定論を差し替える機能は提供しない」と明言 <https://github.com/WebAssembly/wasi-random/blob/main/README.md>）、Extism のホスト関数（plug-in から見ると import）、Javy の `random`（`Math.random` 初回呼び出し時に WASI から seed）
- **per-call 注入の前例**: Secret Network は呼び出しごとに `Env.random` を注入する（<https://docs.scrt.network/secret-network-documentation/development/development-concepts/randomness-api>）。本件の「ABI 要求に添えて渡す」に最も近い。Internet Computer `raw_rand` は非同期のシステム API（32 バイト）、CosmWasm は乱数を持たず外部（Nois）から供給
- 決定論的テストの差し替え: Go `rand.New(rand.NewSource(seed))`、Rust `rand::rngs::mock::StepRng`、Vitest `vi.spyOn(crypto, "getRandomValues")` / `vi.stubGlobal`、Storybook `storybook-addon-determinism`（`crypto.getRandomValues` を seed 付きに差し替え）
- 含意: Rust 側は `rand` に依存せず、渡されたバイト列をカーソルで消費する自前の pool で足りる。テストは `randomProvider` を固定（時計と同じ差し替え口。REQUIREMENTS R2）にすれば Rust 側まで決定論的。「1,024 バイトを使い切ったら例外（伸長しない）」を ABI の契約に明記する（REQUIREMENTS どおり）

### 4.7 作らなくてよいもの（総括）

- 非 2xx 本文の JSON 判定ロジック（ky と同型。独自の判定表は不要）
- 本文上限の正当化（client-go 2 KiB / OTel 4 MiB の前例）
- 408 / 429 除外の根拠（Azure の既定リストを引用）
- 冪等キーの運用規則（Stripe / Shopify / IETF draft をそのまま契約文に）
- 乱数ライブラリ（`rand` / `rhai-rand` / `getrandom` は使わない。自前 pool）
- Worker モックの失敗応答 API（足すなら MSW の `json(body, {status, headers})` の契約を写す）

## 5. plan への材料（設計の選択肢。plan が決めて DECISIONS に書く）

- **A. 失敗本文の受付を 1 関数に**: `failureDetails(response, {optIn, limit: 64_000, signal, reader?})` → `{status, body?, bodyError?}` を `http.js` に置き、request / upload / multipart は `readLimitedBytes` で、download は既存 `reader` で読む（`reader` を渡せる形にする）。Content-Type の正規化・object 判定・理由の列挙はここだけ。Worker モックは内側の `httpAdapter` を通るので自動で効く。却下案: 4 経路に別々に書く（理由の綴りと順序がずれる温床）
- **B. ## 7. 要件への影響（提案。REQUIREMENTS.md は書き換えない）

1. **乱数関数の例外文言の言語**: REQUIREMENTS R2 / R5 は「日本語の契約文言」。既存のネイティブ関数の例外は全部英語（§1.4）で、`docs/native-extensions.md:35` は「例外は `try / catch` で処理できる」としか書かない。plan は (a) 要件どおり日本語にする（Rust の例外文言で初めての日本語。`date.rs` 等との不統一を文書に注記）、(b) 英語にして REQUIREMENTS の該当箇所を「契約文言（英語。既存関数と同じ）」と読み替える（REQUIREMENTS の書き換えは discuss の権限なので BLOCKED になる）、のどちらかを決める。推奨 (a)（要件を変えない。文言はキー付きで文書化すれば十分）
