# OPFSファイル転送の実装方針

記録日: 2026-10-04。状態: 会話で合意した方向性と設計候補。ファイル転送は未実装。操作名・DSL・容量などのAPI契約は未確定。この文書から未登録のRhai関数や操作を生成しない。

## 合意した方向性

OPFSをブラウザ内のファイル作業場所として使い、サーバーとのダウンロード・アップロードを双方向で扱う。OPFSに生成したファイルをアップロードする用途も対象とする。

**multipartは最初から対応する。** 本文をそのまま送る方式だけを先行し、multipartを後回しにする案は採用しない。

想定する利用例:

- CSV・帳票などを生成してOPFSへ保存し、サーバーへアップロードする。
- サーバーからファイルをOPFSへダウンロードし、表示・加工に利用する。
- 加工したファイルを別名で保存し、再アップロードする。
- ファイルと説明・分類などの文字列項目をmultipartでまとめて送る。

## 設計候補

既存のホスト側アダプター方式に沿って転送を追加する。Rhaiは依頼と完了後の画面処理を担当し、ブラウザホストがHTTPとOPFSを操作する。

| 転送                  | 候補となる動作                                        |
| --------------------- | ----------------------------------------------------- |
| ダウンロード          | GETで取得し、指定したOPFS領域・相対パスへ保存する     |
| 本文アップロード      | OPFSのファイルをリクエスト本文としてPUT／POSTで送る   |
| multipartアップロード | OPFSのファイルと文字列項目をmultipart/form-dataで送る |

画面からは接続名・操作名とOPFSの領域・相対パスを指定する構成を基本候補とする。接続URLや認証はホスト設定に置き、JWTなどを画面stateへ渡さない。

ファイル本体はWASMやJSONのstateを経由させず、ホスト側で取得・保存・送信する。完了時は保存先、サイズ、HTTPステータスなどのメタデータを返す方向とする。保存完了後に一覧やプレビューへつなぐ。

multipartの候補項目は、フォームのファイル項目名、送信時のファイル名、ファイルのContent-Type、追加の文字列項目。FormDataのboundaryはブラウザに任せ、画面から手動指定させない。

## 現行実装との境界

- [OPFSの現行契約](files-cache-rpc.md)にはテキスト・バイナリの読み書きがある。テキスト100 KB、バイナリ1 MBなどの上限は現行APIの契約であり、新しい転送APIの容量は別途決める。
- [HTTPアダプター](http-adapter.md)はJSON本文送信とjson/text/empty応答に対応する。ファイル本文・multipart送信や、HTTPからOPFSへ直接保存する操作は未実装。
- [WorkerモックAPI](worker-mock-api.md)はJSONの固定応答・CRUD用。今回のファイル転送やmultipartを既に扱えるとは考えない。
- 本番バックエンドのBun／TypeScript構成は別途検討する。今回の記録ではバックエンド製品やDBを確定しない。

## discuss／researchで確定する項目

1. アダプターの分け方、操作名、DSL、接続とOPFS領域の宣言・参照方法。
2. multipartの複数ファイル、同じ項目名の複数値、対応メソッド、文字列項目の型と上限。
3. 容量上限、ストリーム転送の範囲、タイムアウト、進捗表示、中止の扱い。
4. 保存先の上書き、親ディレクトリ、途中ファイルの処理、失敗時の既存ファイル保持。
5. OPFSの排他と画面切替時の寿命。送信済みの更新を中止で巻き戻せない場合の完了・エラー契約。
6. 成功メタデータ、アップロード応答本文、HTTPエラー、CORS・認証と再送方針。
7. DOM／Canvasのサンプルと、ダウンロード→加工・生成→multipartアップロードを確認できるテスト用サーバー。
