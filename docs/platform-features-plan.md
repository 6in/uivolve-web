## 順序と成果物

1. `stateSchema`とWebMCPのメタデータを追加。既存パッケージはどちらも省略できる。型・必須・null・配列・オブジェクトと文字列/数値/配列の範囲を扱い、未対応属性は拒否する。型付き入力のbindとの整合も確認する。
2. YAMLの解析とエディタ、画面URLの解決を共通ホストモジュールへ分離。絶対baseを使用し、深いURLでもWASM・アセット・同梱ファイルを正しく取得する。
3. 保存依頼・完了のABIを追加。IndexedDBはページごとのキー、OPFSはページごとのJSONファイルを使う。実際の保存成功後に完了を返し、画面置換時は処理の中止と古い応答の破棄を行う。
4. YAML・型・WebMCP情報を持つ保存デモを追加。両方式から保存/復元/削除、再読み込み後の保持を確認する。
5. 実WASMとホストのテスト、ブラウザ確認、ビルド・静的チェック・文書リンク確認を行い、計画書へ結果を追記してコミットする。

## 保存の責務と制限

WASMはブラウザの保存APIへ直接アクセスできないため、既存のHTTP依頼と同じ「検証後の依頼→JSホスト→完了通知」を使う。JWTや認証情報を自動保存しない。保存対象はページが明示したJSONだけで、1値1 MB以内、同名の同時要求は1件に限定する。

IndexedDBはトランザクションのcomplete後、OPFSは書き込みストリームのclose後に成功を通知する。画面を切り替えても、すでに確定した保存を巻き戻すことはできない。開始済みの処理は可能な範囲で中止し、遅い完了通知は旧画面へ適用しない。永続保存容量、ブラウザによる削除、プライベートモード、OPFS未対応/secure contextの条件は通常の失敗としてRhaiへ返す。

参考：[IndexedDBのトランザクション](https://developer.mozilla.org/en-US/docs/Web/API/IDBTransaction)、[OPFSの取得](https://developer.mozilla.org/en-US/docs/Web/API/StorageManager/getDirectory)、[OPFS](https://developer.mozilla.org/en-US/docs/Web/API/File_System_API/Origin_private_file_system)。

## URLと配信

ページのルートだけを`index.html`へフォールバックする静的サーバー設定が必要。Viteの開発/プレビューでも確認する。同梱資源の404へHTMLを返す運用は避ける。配信先がサブディレクトリの場合はビルド時のbaseを指定する。ReactRouterの導入は必要ない。

## 今回省略するもの

5項目の基本機能はすべて実装できた。難しさによる項目全体のスキップはない。今回の範囲を超える次の機能は省略した。

- OPFSの任意ディレクトリ操作・バイナリ/巨大ファイル・Worker上の同期アクセス・IndexedDBの任意DB/索引/複数キー一括トランザクション。OPFSのファイルAPIとアプリキャッシュは[後続の検討書](opfs-cache-rpc-investigation.md)に実装案を記載した。ここでの実装範囲はJSON保存のまま。
- 保存容量の予約、永久保持の保証、サーバーとの同期、ページの配信元ごとの認可。ページidによる領域分離は同一オリジン内のセキュリティ境界ではない。
- 任意のURLパラメータをRhaiへ渡すルートDSL、SSR、外部パッケージの自動ルート登録。
- YAMLの独自タグ・循環/エイリアス・複数ドキュメント・日付型などJSONへ素直に変換できない値。
- WebMCPのページ固有ツール自動生成と任意handlerの直接呼び出し。説明メタデータは認可やツール実行命令を代替しない。
- 完全なJSON Schema（`$ref`、組合せ、条件分岐など）とRhaiコードの静的型検査。今回の型検証はDSLが宣言したデータの検証。
